YoloRSA

A ladder of deliberately-weak textbook RSA "wallets," each sized to a specific real-world cracking difficulty — from mental arithmetic up to "needs a real factoring tool." The idea: deploy one, fund it with testnet ETH, publish nothing but its public key (baked directly into the contract's own bytecode), and see how long a stranger takes to factor the modulus, recover the private exponent, forge a signature, and drain it.

:::info Never send a private key on-chain Every .read() call — even a pure function, even against a fully local simulated network — ships its calldata as plaintext to whatever node executes it. A real private scalar must never be a call argument against a real RPC endpoint; it stays local, full stop. This repo's own tests only pass raw private keys as .read() args against Hardhat's in-process network, purely to exercise on-chain arithmetic against a known value — see the caveats at the top of YoloRSA.test.ts. :::

The difficulty ladder​

Tiertarget bitscracked bytypical time
pencil~12mental trial divisionunder a minute, by hand
calculator~24a phone calculator / one-line scriptseconds
script-kiddie~48naive Pollard's rho, any languagewell under a second
laptop~80Pollard's rho with a real bignum libseconds to low minutes
weekend-project~248a real factoring tool (YAFU/msieve, SIQS)roughly an hour or few, one consumer CPU core

weekend-project sits at 248 bits, not higher: n has to fit in a single 32-byte EVM word — 256 bits is a hard ceiling for this template, not just a target. (See the wide tiers for what happens once a tier genuinely needs to exceed that.)

One honest caveat worth internalizing: these estimates were calibrated against this repo's own naive factor() helper (trial division, then Pollard's rho) — a real attacker who already knows to reach for a proper GNFS-based tool (CADO-NFS, msieve) cracks every tier here, including weekend-project, in well under a minute. The ladder is genuinely hard only against someone who doesn't yet know that. See LightningRSA's page for the GNFS-based methodology that actually accounts for real tooling.

Message representative — no real padding, on purpose​

Real RSA signature schemes (PKCS#1 v1.5, PSS) need the modulus to be significantly wider than the digest they embed — a 2048-bit modulus for a 256-bit SHA-256 digest, with room to spare. None of YoloRSA's moduli (12-248 bits) have that room, so there's no structured padding at all: the message representative is simply

m = msgHash mod n

This is deliberately more broken than "just" a factorable modulus — textbook RSA without padding has malleability/forgery issues independent of factoring (e.g. sig(m1) * sig(m2) mod n == sig(m1*m2 mod n)), which is fine, even desirable, for a wallet whose whole purpose is getting cracked.

Verification​

function verify(uint256 n, uint256 e, uint256 signature, uint256 msgHash) internal view returns (bool) {
    if (n == 0 || signature >= n) return false;
    uint256 m = msgHash % n;
    return _modexp(signature, e, n) == m; // s^e mod n == m, via the MODEXP precompile
}

The deployable Yul account (YoloRSAAccount.yul) re-inlines this exact check using only the MODEXP precompile, per the validation-trace constraint — same relationship NostrFrameAccount.yul has to BIP340.sol. One compiled account template is redeployed unmodified across every tier; only the constructor args (e, n) differ per deployment, so adding a new tier never means recompiling new bytecode.

The attacker's side​

test/js/utils/yoloRSA.ts implements both halves: generateKeypair/sign/verify (the owner's side — d never leaves this process) and factor/crackPrivateExponent (the attacker's side — trial division, then Pollard's rho). scripts/gen-yolo-rsa-vectors.ts runs the full crack round-trip during vector generation itself, for every tier through laptop, as a sanity check that the tier is actually as weak as intended — not just "small," but demonstrably factorable by the bundled naive tooling.

Layout​

  • contracts/src/YoloRSA/YoloRSA.sol — the verify library, forge-tested (test/solidity/YoloRSA/YoloRSA.t.sol) against every tier's known-answer vectors.
  • contracts/src/grimoire/YoloRSA/YoloRSAAccount.yul — the deployable account. Storage slot 0 = e, slot 1 = n; constructor takes both as two right-aligned words appended after initcode.
  • contracts/test/js/utils/yoloRSA.ts — keygen, sign, verify, factor, crack — pure bigint, no EVM.
  • contracts/scripts/gen-yolo-rsa-vectors.ts → contracts/test/vectors/yolo-rsa-vectors.json — regenerate any time; these are test fixtures, safe to commit. A real deployed challenge must generate its own keypair locally and never commit d.
  • contracts/test/js/YoloRSA.test.ts — pinned vectors plus a live sign → verify → crack → forge round trip, proving the break is real, not just asserted.

Related​

  • YoloRSA: wide tiers — the same ladder extended past 256 bits (two EVM words), sized against a real GNFS cost model instead of "small enough to factor with a naive script."
