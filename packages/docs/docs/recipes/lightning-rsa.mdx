# `LightningRSA`

A self-verifying EIP-8141 account authorized by a **real** RSASSA-PKCS1-v1_5/SHA-256 signature (RFC 8017 §9.2/§8.2) — unlike the grimoire's [`YoloRSA`](../grimoire/yolo-rsa.mdx) (deliberately tiny, deliberately unpadded), this is meant to be sound at any modulus width an operator actually deploys with. Default target: RSA-2048.

:::note Why "LightningRSA," reused from a toy that moved
An earlier design used this name for a *deliberately crackable* wide-modulus wallet, sized against a chosen time window. That idea didn't go away — it moved to the grimoire as [`YoloRSA`'s wide tiers](../grimoire/yolo-rsa-wide.mdx), once it became clear modulus size was never what made it a toy (unpadded RSA never becomes sound, at any size). This page is the name's second, and correct, home: a recipe that's actually meant to be trusted.
:::

## What makes this a recipe, not a grimoire entry

The dividing line isn't deployability — `YoloRSA` is equally deployable. It's whether the underlying scheme is *sound*:

- **[`NostrFrameAccount`](./nostr-frame-account.mdx)** wraps real, audited BIP-340 Schnorr in a novel account-abstraction context.
- **`LightningRSA`** wraps real EMSA-PKCS1-v1_5 padding (RFC 8017 §9.2) the same way — full padding reconstruction, not the "no room for padding at all" shortcut `YoloRSA`'s tiny moduli are stuck with.

## `n` is arbitrary width — Solidity's `bytes`, not a fixed word count

`YoloRSAWideAccount` hand-rolled a 2-word modulus. `LightningRSA.sol`'s library takes `n`, `e`, and `signature` as plain `bytes memory` — Solidity's own arbitrary-length type already gives full "N words" generality, and the `MODEXP` precompile (`0x05`) natively accepts arbitrary-length `Bsize`/`Esize`/`Msize` operands (real production RSA-2048 on-chain verifiers already do exactly this). RSA-2048 → `n` is 256 bytes → 8 EVM words; retargeting to RSA-3072/4096 is a keygen parameter change, not a rewrite.

```solidity
function verify(bytes memory n, bytes memory e, bytes memory signature, bytes32 msgHash) internal view returns (bool)
```

`msgHash` plays the role of "the message" — it gets hashed *again* with SHA-256 internally, exactly like any RS256-signed payload. Passing an already-hashed value (a Frame tx's `compute_sig_hash(tx)`) into a hash-then-sign scheme is completely normal, not a bug.

## Recompute the expected block, never parse the recovered one

Verification re-derives the expected padded block (`EM`) from the message hash and compares it byte-for-byte against `MODEXP`'s recovered output — it does **not** parse padding out of the recovered value. This is deliberate: implementations that leniently *parse* PKCS#1 v1.5 padding (permitting garbage after the DigestInfo, or a too-short padding string) instead of reconstructing-and-comparing are exactly the ones that have historically been broken — Bleichenbacher-style low-exponent forgeries against sloppy verifiers, real bugs in OpenSSL/NSS/Firefox in the 2000s-2010s. Recompute, don't parse.

```
EM = 0x00 || 0x01 || PS (0xff * psLen) || 0x00 || T
T  = SHA256_DIGEST_INFO_PREFIX (19 bytes, RFC 8017) || H(msgHash)
```

Every value in this construction is cross-checked against real signatures — not just internally consistent, the same discipline [`BIP340.sol`](./nostr-frame-account.mdx) applies against `nostr-tools`. Here the reference is Node's own `crypto` module: `scripts/gen-lightning-rsa-vectors.ts` generates a real RSA-2048 keypair, signs with Node's real `crypto.sign`, and checks two things before trusting a vector — that Node's own `crypto.verify` accepts Node's own signature, and that this repo's from-scratch reimplementation agrees with it.

## The gas budget forced a real design decision: `e = 3`, not `65537`

EIP-8141 caps a `VERIFY` frame's total public-mempool-admissible execution at `MAX_VERIFY_GAS = 100,000` — confirmed against the EIP text directly, not assumed: *"The sum of `limits.execution` values across the validation prefix, plus the intrinsic cost of validating `tx.signatures`, must not exceed `MAX_VERIFY_GAS`."*

`MODEXP`'s EIP-2565 gas formula prices its `iteration_count` from the **exponent's** bit length, not the modulus's. At the usual public exponent `e = 65537` (17 bits), a single RSA-2048 `MODEXP` call costs roughly 200,000 gas by that formula — already over budget before SHA-256, padding reconstruction, or anything else runs. At `e = 3` (2 bits), it drops to roughly 13,000.

A forge-measured run of the Solidity reference library confirms this empirically:

```
LightningRSA.verify gas used: 92187
```

(`test_gasCost_underVerifyFrameBudget` in `LightningRSA.t.sol`, `assertLt(gasUsed, 100_000)`.) That figure is for the Solidity library specifically — `bytes memory` indexing overhead dominates it more than `MODEXP` does. The deployed Yul account avoids that overhead entirely (raw `mstore8`/`mload` throughout), so its actual on-chain cost is expected to be lower still, though — consistent with every other EIP-8141-opcode-using account in this repo — it isn't independently measurable without the live testnet.

Low-public-exponent RSA has real historical forgery bugs, but every one of them targeted verifiers that parsed padding leniently. Recompute-and-compare closes that class regardless of `e`'s size — see the section above.

## Why `n`/`e` live in the deployed code, not storage

A real RSA-2048 modulus is 8 EVM words. Reading 8 words via `SLOAD` — even warm — costs far more than reading the same 8 words via `CODECOPY` from the contract's own bytecode, and with a 100,000 gas ceiling in play, that difference matters. `LightningRSAAccount.yul`'s constructor appends `[n][e][nLen]` directly after its own runtime code at deployment (`return`ing a buffer wider than just the runtime object), and every call re-derives them with a cheap self-`CODECOPY`, bootstrapped the same "read from the end of `codesize()`" trick the constructor itself uses to find its own appended args.

## Verified two ways before trusting the Yul port

1. **The math**: `LightningRSA.sol`, forge-tested against real RSA-2048/e=3 signatures (`test/solidity/LightningRSA/LightningRSA.t.sol`), including the gas-budget assertion above.
2. **The Yul translation**: rather than trust hand-checked offset arithmetic, `test/yul/LightningRSAAccountVerifyHarness.yul` — a test-only mirror of the account's verify function with `SIGDATACOPY`/`TXPARAM`/`APPROVE` swapped for plain calldata (so it's callable on Hardhat's ordinary network, unlike the real account) — is deployed and checked against the *exact same* real vectors, confirming identical accept/reject verdicts to the Solidity original.

Plus `LightningRSAAccount.test.ts`, which deploys the real account (not the harness) and proves the constructor's code-embedding and the `e()`/`n()` getters' bootstrap read are correct — the one part of the real account that doesn't need EIP-8141 opcodes and so is directly testable.

## Layout

- `contracts/src/LightningRSA/LightningRSA.sol` — the verify library.
- `contracts/src/LightningRSAAccount/LightningRSAAccount.yul` — the deployable account.
- `contracts/test/js/utils/pkcs1.ts` — Node-crypto-backed keygen/sign/verify reference.
- `contracts/scripts/gen-lightning-rsa-vectors.ts` → `contracts/test/vectors/lightning-rsa-vectors.json` — regenerate any time; a **fresh** keypair every run, fine to commit (these are test fixtures — a real deployment must generate its own keypair locally and never commit the private key, same rule as every other recipe and grimoire entry here).
- `contracts/test/solidity/LightningRSA/LightningRSA.t.sol`, `contracts/test/js/LightningRSAAccount.test.ts`, `contracts/test/yul/LightningRSAAccountVerifyHarness.yul`.
