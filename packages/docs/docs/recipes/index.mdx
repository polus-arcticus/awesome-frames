# Recipes

A Frame account recipe is: a `VERIFY`-frame target contract, a signature scheme, and a script proving the round trip against a live (or simulated) Frame-tx-capable network.

- **[`NostrFrameAccount`](./nostr-frame-account.mdx)** — authorized by a BIP-340/Nostr Schnorr signature instead of ECDSA.
- **[`LightningRSA`](./lightning-rsa.mdx)** — authorized by a real RSASSA-PKCS1-v1_5/SHA-256 signature, arbitrary modulus width.

## Adding a new recipe

1. **Write the account contract.** Solidity is fine unless you need EIP-8141's own opcodes directly (custom `APPROVE` scope logic, reading `TXPARAM`/`SIGDATACOPY`) — in that case it has to be Yul, compiled directly with `solc` (`hardhat compile` doesn't handle `.yul` files, only `.sol`). Remember the [validation-trace rule](../eip-8141.mdx): no external calls out of a `VERIFY` frame except to `tx.sender`, a default-code account, or a precompile.
2. **Decide your signature scheme.** `SECP256K1`/`P256` need no custom verification code at all (the protocol checks them) — reach for `ARBITRARY` only when you actually want bespoke verification logic, and put the witness bytes in an `ARBITRARY` signature entry with an empty `msg` (never in frame `data`).
3. **Build and submit the transaction** with [`viem-frame-tx`](../viem-frame-tx.mdx): construct a `FrameTransactionSerializable`, sign `computeSigHash(unsigned)` with your scheme, attach it to `signatures`, call `serializeFrameTransaction`, and submit via ordinary `sendRawTransaction`.
4. **Test it two ways**: a pure-library/no-EVM-context unit test for the verification math itself (fast iteration, easy known-answer vectors), and a real submission against `ethrexTestnet` (or a Hardhat-simulated equivalent, for anything that doesn't need EIP-8141's own opcodes) for the actual account-contract integration.
